3. **禁止修改 `corpus/` 下任何文件。** 语料是唯一事实源，你是来核验它的，不是来补它的。
4. 报告里**不允许出现**下列无主语空话，出现一处，该段落作废：
   - "整体表现良好" / "基本满足需求" / "体验流畅"
   - "建议进一步优化" / "可以增加更多功能" / "建议加强测试"

5. 不要先读 `_archive/review/report.md`（上一轮另一家模型的评审结论）。**你先独立打分**，全部写完后再可选用它做交叉对照，且对照内容只放第 9 节。

## 2. 必做动作（七组，缺一组则该维度不得分）

### A 组 · 事实准确性（对应 30 分）

1. 跑 `python tools/regress.py` 与 `python tools/regress.py --ask`，记录两份通过数。
   - **不要直接采信脚本的 PASS/FAIL。** 脚本的判据是"标题命中关键词"，你还要自己判断**答案正文和引用原文是否一致**。脚本判 PASS 但你核出编造的，按编造扣分。
2. 从回归集 20 题里挑 **全部 20 题**，逐题做下面这件事（这是本次验收的核心工作量，不许抽样省略）：
   - 记录 `/api/ask` 返回的 `answer` 全文和前 3 条 `citations`；
   - 用 `citations` 里的 `doc_uid` + `chunk_id` 回到 `corpus/docs_final.jsonl` 取原文；
   - 逐句比对：**答案里每一个数字、期限、材料清单、办理地点，是否都能在引用原文里找到**。
   - 找不到的写进"编造清单"，格式：`问题 | 答案原句 | 引用原文实际内容 | 性质(编造/夸大/张冠李戴/过期版本)`。
3. 另外自拟 **5 个语料明显不覆盖**的问题（例如外地户籍入学、教师岗位工资、食堂承包商、宿舍 WiFi 密码、校领导办公电话），验证是否拒答而不是硬凑。自拟题要写清"为什么你认为语料不覆盖"，并给 `grep` 证据。
4. 版本冲突探测：找一对**新旧版本**文件（如同一制度 2023 与 2026 版），问一个两者规定不同的点，看它引的是哪一版、有没有提示"以新版为准"。

### B 组 · 边界与拒答（12 分）

- 统计：该拒的题（语料 0 命中）里拒了几条、硬答几条；该答的题里误拒几条。
- 拒答时是否给出**可操作的替代问法**，还是只丢一句"没收录"。
- 越界问题（研究生/教师/校外人员视角）混进来时，是否明确区分适用对象，而不是拿本科生规定硬套。

### C 组 · 响应速度（15 分）

1. 跑 `python tools/selftest_speed.py`，记录 10 条问题的 `首字节 / 首字 / 完成` 三个时间。
2. 自己再测 **5 条长问题**（60 字以上、含多个限定条件），取 p50 / p90。
3. 冷启动测一次：杀掉服务重启后立刻发第一个请求，记录首个请求耗时（冷启动是否明显劣化）。
4. 确认流式是真流式：用 `curl -N` 观察 `/api/ask/stream`，记录第一帧 `meta` 与第一个 `delta` 的到达时间差。**若 `meta` 里带了完整答案或 `final` 先于 `delta`，判为假流式，本项不超过 8 分。**

### D 组 · 交互与可追溯（13 分）

读 `web/app.html`（776 行，单文件，含 CSS/JS），重点核：

- 引用卡能否展开看原文片段；能否证明"这句话对应文件第几段第几句"（找 `sent_no` 的落点）；
- 同一页多轮问答时，引用编号是否会串（找 `data-n` 一类的处理）；
- 错误态（400/500/网络断）用户看到的是人话还是 `undefined`；
- 键盘可达性：Tab 顺序、焦点可见、`aria-label` 是否只是摆设（说清哪些元素有、哪些关键控件没有）；
- 首屏到能提问，需要几步操作。

### E 组 · 阅读舒适度（12 分）

- 量 CSS 里的实测值：正文 `font-size`、容器 `max-width`、行高，换算成**每行中文字数**，判断是否落在 30–45 字。
- 对比度：正文/次要文字/链接三档颜色各算一次对比度，低于 4.5:1 的列出来。
- 长答案（>400 字）是否可扫读：有无小标题、要点、结论前置。
- 移动端：`body`/`main` 的高度处理是否会让输入框被挤出视口（查 `100dvh`、`flex`、`min-height:0` 这类处理），并说明你的判断依据。
- 若你有截图能力，补 375 / 768 / 1440 三档实测；没有就明确写"本节为静态推断，未做视觉核验"，**不许假装看过**。

### F 组 · 健壮与降级（10 分）

逐项探测，记录实际返回而非想象：

1. 模型不可用（`config.json` 里把 key 改错太危险——改为：直接观察代码里 `degraded` 分支的触发条件，并用一个 0 命中的问题触发降级路径）。降级时界面上是否诚实标注，还是照旧盖"已核验"章。
2. 超长输入（201 字）、空串、纯符号、SQL/HTML 注入串、emoji。
3. 并发 5 个不同问题同时打（写个小脚本），记录是否有 5xx、是否串答案。
4. 缓存：`/api/status` 的 `cache_hits` / `cache_size`，判断缓存是否真的生效、有没有缓存住过期答案的风险。

### G 组 · 工程可维护性（8 分）

- `server.py` 1447 行单文件，评估职责是否可切分（只给结论 + 最该切的 2 处，不要写重构方案）；
- `tools/regress.py` 的判据是否真能判出内容错误（它历史上出过"只要接口返回 ok 就算 PASS"的问题，现在改成了标题匹配——你觉得够不够）；
- `README.md` / `AGENTS.md` 里写的能力，与代码实际能力是否一致，列不一致处；
- 有无死代码、注释与实现相反的地方（举 1–2 例即可）。
