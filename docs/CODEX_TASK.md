## 1. 已修复的问题（不要再动这部分）

**现象**：换到 `deepseek-flash` 后，同一个问题连续三次耗时 7.5s / 10.0s / 30.2s，
结果时对时错，答案层从 20/20 掉到 19/20。

**根因**：`deepseek-flash` 默认开启推理模式，响应里带 `reasoning_content`。
思考 token 计入 `max_tokens`，配额被吃满时正文为空：

| 配置 | 耗时 | 思考 token | 正文字数 |
|---|---|---|---|
| 默认（max_tokens=700） | 5.8s | 557 | 244 |
| 默认（max_tokens=700） | 6.8s | **700（吃满）** | **0** |
| thinking=disabled | 2.2s | 0 | 380 |
| thinking=disabled | 2.4s | 0 | 452 |

**已在 `llm.py` 修复**（已实测，勿回退）：

1. `payload` 加 `"thinking": {"type": "disabled"}`（旧模型会忽略该字段，实测兼容）
2. `max_tokens` 700 → 1500
3. 空正文自动重试一次，仍为空则抛 `RuntimeError` 并带上 `finish_reason`

**修复后实测**：同一问题连续 4 次全部成功，2.3–3.5s；评测 20/20 / 20/20 / 5/5，单题 2.0s。

## 3. Token 成本实况（优化前请先看这个）

实测 5 条问题的用量（`deepseek-flash`，官方定价空闲价：缓存命中 0.02 元/1M、
未命中 1 元/1M、输出 4 元/1M；高峰翻倍）：

| 问题 | 输入 | 缓存命中 | 输出 |
|---|---|---|---|
| 学生证丢了 | 1392 | 1152（83%） | 101 |
| 国家奖学金条件 | 5080 | 4864（96%） | 199 |
| 考试作弊 | 5991 | 5760（96%） | 272 |
| 校园卡丢了 | 3199 | 2944（92%） | 134 |
| 学分绩点 | 7953 | 7808（98%） | 211 |
| **平均** | **4723** | **~95%** | **184** |

**成本结构（单题，空闲时段）**：

- 输入命中 4487 × 0.02/1M = 0.00009 元
- 输入未命中 236 × 1/1M = 0.00024 元
- 输出 184 × 4/1M = **0.00074 元**

**输出占 70% 成本，输入虽占 96% 的 token 却只占 30% 的钱。**
所以"砍资料块"几乎不省钱，"压输出"才省钱。
另外关闭思考已经把输出从 ~800 token 降到 ~200，这是目前最大的一笔优化（省约 75%）。

## 4. 任务

### T1 修复 `eval.py` 的 `--llm` 语义（P0，低）

不带 `--llm` 时也会调模型，跑一轮 50 秒，但文档写的是「秒级自检」。

- 不带 `--llm`：只跑检索层（`R.search`），不调模型；答案层、拒答层标「跳过」，不计入分母
- 带 `--llm`：完整三层

**验收**：`python eval.py` 5 秒内完成；`python eval.py --llm` 约 50 秒且 20/20、20/20、5/5。

### T2 为 `_intent_mismatch` 建回归测试（P0，中）

这条规则是硬编码正则，已经出过一次误拦事故：
「转专业什么时候可以申请」被判"没收录"，而语料原文明确写着"一年级第一、第二学期"。

新建 `test_rules.py`，至少 24 条，每条跑真实 `server._intent_mismatch(q, groups)`，不许 mock：

| 类别 | 期望 |
|---|---|
| 钟点类、语料无钟点（食堂几点开门、图书馆开放时间、校车时刻表） | 拦截 |
| 钟点类、语料有钟点（第一节课几点上课、作息时间表） | 放行 |
| 周期类、语料有学期（转专业什么时候可以申请、奖学金什么时候评、毕业设计什么时候开题） | 放行 |
| 周期类、语料无依据（2026年校历什么时候开学、军训什么时候开始） | 拦截 |
| 学费类（学费一年多少钱、住宿费多少钱） | 拦截 |
| 无关干扰（考试作弊怎么处理、学分绩点怎么计算） | 放行 |

**验收**：全绿；故意改坏一个正则，测试必须变红。

### T3 控制输出长度（P1，低）—— 省钱效果最大的一项

输出单价是输入命中的 200 倍，且当前 `max_tokens=1500` 是"上限"而非"目标"。

- `max_tokens` 1500 → **600**（正常输出 200–400 token，不受影响，只拦偶发超长）
- 把 system prompt 第 11 条「逐项覆盖、不能为简短而省略」改成有上限的表述：
  「要素较多时按重要性取前三项，其余归纳为一句话，整体不超过 300 字」

**验收**：`python eval.py --llm` 仍 20/20；实测平均输出 token 从 184 降到 150 以内。

---

### T4 问题级答案缓存（P1，中）—— 命中即 0 token

同一问题短期内被重复问的概率不低（新生集中咨询）。

- 用问题规范化后的字符串（去空格标点、同义表述归一）做 key，命中直接返回上次答案
- 内存 LRU，容量 200，TTL 24 小时
- 命中时 `/api/ask` 返回 `"cached": true`，前端标签显示「缓存结果」
- 涉及事实层更新（`add_fact.py`）时清空缓存，避免返回过期答案

**验收**：同一问题问两次，第二次 < 50ms 且 `cached=true`；改一条事实后缓存失效。

### T5 把 token 用量暴露到接口（P1，低）

`llm.LAST_USAGE` 已在 `llm.py` 里维护（本次改动加的，勿删）。

- `/api/status` 增加 `last_usage`（输入/命中/输出）

**目的**：让成本可见，否则没人会发现"输出比输入贵 200 倍"这件事。

**验收**：接口返回真实数值，与 `LAST_USAGE` 一致。
